# Decision log

One or two lines per decision: what was chosen and why. Newest decisions are appended at the end of each section.

## Step 0: repository and toolchain

- **Repository classification: (a) empty.** The working directory contained nothing; the project was scaffolded from scratch on the default stack.
- **Node 24 LTS, npm.** pnpm was installed but its tarball downloads go to `registry.npmjs.org`, which resets TLS connections on the build network. npm rewrites tarball hosts to the configured registry, so npm with `registry.yarnpkg.com` (the same npm registry content served through Cloudflare) installs reliably. The project `.npmrc` pins that registry; delete the line to use the default registry.
- **Postgres 17 in Docker on host port 5433.** Docker Desktop was available (started on demand). Port 5432 was taken by an unrelated local Postgres, so Compose publishes 5433; `POSTGRES_PORT` overrides it. An init script creates the separate `audittrail_test` database.

## Stack

- **Next.js 16 (App Router, React 19, Turbopack), TypeScript strict with `noUncheckedIndexedAccess`.** Docs were read from `node_modules/next/dist/docs` because Next 16 changed several APIs (async request APIs only, `proxy.ts` replaces `middleware.ts`, `next lint` removed, `next typegen`).
- **Prisma 7 with the `prisma-client` generator and `@prisma/adapter-pg`.** Prisma 7 requires a driver adapter and `prisma.config.ts`; the generated client lives in `src/generated/prisma` (git-ignored, regenerated on `postinstall`). The CLI is pinned to 7.10.0 because the registry's `latest` tag pointed at an 8.0 release candidate.
- **Tailwind CSS 4 with hand-written shadcn-style components on `radix-ui` primitives.** The shadcn CLI is interactive and needs network access to its registry; the components it would generate (button, dialog, popover, dropdown, tooltip, tabs, command, sheet) are written directly in `src/components/ui` in the same style.
- **Forms use Server Actions with `useActionState` and zod field errors instead of react-hook-form.** Every form posts to a Server Action that validates with the same zod schema and returns field errors, which gives progressive enhancement and one validation path. react-hook-form would add a second, client-side state model without changing security.
- **Tables are server-rendered with URL state instead of TanStack Table.** Filtering, sorting and pagination happen on the server (Section 9.5 requires URL query state and 50-row server pagination), so a client table engine added no value.
- **No chart library.** Readiness bars and the status distribution are plain CSS bars with counts.

## Authentication

- **First-party database-session auth instead of Better Auth.** Better Auth stores session tokens and password-reset identifiers in plaintext and writes them outside our transactions. The spec requires hashed, single-use reset tokens, audit events written in the same transaction as each auth change (`user.logged_in`, `member.logged_in` per org, `session.revoked`), DB-backed rate limits per IP and per IP+email, and timing equalization. Implementing those around Better Auth would mean bypassing most of it, so the spec's fallback applies. As a result there is no `/api/auth/[...all]` route: sign-in, sign-up, sign-out and password flows are Server Actions.
- **Opaque 256-bit session tokens, stored as HMAC-SHA256 (keyed with `AUTH_SECRET`).** The same scheme hashes password-reset and invitation tokens. A database leak alone yields no usable tokens.
- **Sessions: 7-day idle expiry, refreshed at most once a day, with a 30-day absolute lifetime.** The cookie lives 30 days, and the database enforces both limits. On https the cookie uses the `__Host-` prefix.
- **scrypt (N=2^15, r=8, p=1) for passwords.** It is memory-hard, built into Node and needs no native build step (argon2 would need a compiled addon on Windows and in Docker). Parameters are stored per hash.
- **An extra per-email login limit (10/min) on top of the spec's per-IP and per-IP+email limits.** Without a trusted proxy the client IP cannot be known, and with one an attacker could still rotate source IPs; the per-account limit stops password spraying against one account either way.
- **`TRUST_PROXY` is a hop count, default 0.** At 0, `X-Forwarded-For` is ignored entirely, because Next.js only fills it when absent and a client could otherwise spoof it. At N > 0, the Nth entry from the right is used.

## Data model

- **UUIDv7 IDs as text columns.** They are unguessable, time-ordered and generated by Prisma (`uuid(7)`) or by `src/server/ids.ts` when an ID is needed before insert (storage keys).
- **Composite foreign keys `(organizationId, id)` on every join table**: ControlRequirement, ControlReview, EvidenceRequirement, EvidenceVersion, ControlEvidence, TaskControl and RiskControl. A requirement-specific evidence link also has a composite FK `(evidenceRequirementId, controlId)`, so it can only point at a requirement of the same control.
- **Raw SQL is limited to what Prisma cannot express**: the append-only trigger, partial unique indexes that prevent duplicate evidence links, and CHECK constraints (the N/A reason is required, LINK evidence must be http(s), slug format, lowercase emails). Trigram GIN indexes are declared in `schema.prisma` (`ops: raw("gin_trgm_ops")`) so `prisma migrate dev` shows no drift; `pg_trgm` is created in the first migration.
- **`@@unique([organizationId, templateId])` on Control** makes framework adoption idempotent at the database level, not just in code.

## Audit trail

- **The hash covers every stored field except `id` and `hash`.** That is a superset of the spec's minimum list (it adds the actor email, name and role snapshots, the resource label, IP, user agent and request ID), so editing any of them is detected.
- **Verification also compares the last event with `AuditChainHead`.** That detects events removed from the end of a chain, which sequence and `prevHash` checks alone cannot.
- **`member.logged_in` records the actor's role in each organization** through a per-event `actorRole` override.
- **Added the `user.profile_updated` action** so name changes are audited like every other mutation.

## Environment

- **`DEPLOYMENT_ENV=local|production`, separate from `NODE_ENV`.** `next start` on a laptop is `NODE_ENV=production`, but it must still be allowed to use the local storage driver for the verification loop. Production validation (`DEPLOYMENT_ENV=production`) rejects the local storage driver, the console email driver, a non-https `APP_URL` and a missing `CRON_SECRET`, and the demo seed refuses to run there unless `ALLOW_DEMO_SEED=true`.
